# 第三批增量：上传暂存的所有权与崩溃回收

日期：2026-10-11。B3-52，关联 R003/R004/R075。状态：源码实现与语法检查，尚未编译、类型检查或执行；第三批未完成。

## 当前调用与问题

`App::bootstrap` 已通过 `capability_delivery::cleanup_uploads` 回收已失去拥有者的上传。本轮检查的是这条真实生产调用，未运行清理或修改本机安装数据。

原清理遇到 UUID 形式的上传目录而没有可识别标记时，会尝试删除空目录。创建上传恰好有“新建目录—建立标记”的中间阶段，另一进程启动清理可能与之竞争。现在无标记、损坏标记及无法证明所有权的目录全部保留；UUID 或空目录本身不构成回收依据。

原 `State::drop` 无条件按固定文件名删除正文，即使 `create_new(body)` 尚未成功。现在明确记录正文是否由本次创建；创建失败的同名既有文件不删除。没有持有自己标记句柄的旧 State 也不凭目录名删文件。

## 源码调整

- Windows 拥有者标记不共享删除权限，活动期间不能按同一路径重命名或替换；使用打开重解析点的标志并检查同一个句柄的元数据。Linux/macOS 使用不跟随符号链接和非阻塞排他 flock，处理中断重试；其他平台不启用未实现的所有权机制。
- 上传根目录规范化并检查仍位于指定配置内；删除前再检查任务及父目录。未知文件只保留，不递归删除任务目录。
- 正文在持有拥有者句柄期间回收，随后关闭句柄，再移除标记与空目录。另一回收进程竞争时可以留下待下次回收的小标记，不能因此删除活动任务的数据。
- 只有既定完整标记且没有活动拥有者时才处理孤立上传；标记读取限制为固定长度加一字节，不因检查之后的文件增长进行无界读取。
- 没有新增界面、文案、依赖或构建资源，也没有把用户目录交给清理脚本。

Windows 文件共享与 Unix advisory flock 的强制性不同；跨平台源码不替代各平台原生验证。完整恶意重解析并发、目录句柄固定及其他暂存类型仍需独立检查，不能把这些路径复查称为通用文件系统沙箱。

## 已准备但未执行的检查

新增用例覆盖无标记创建阶段、损坏标记保留、正文创建失败保留同名文件、Windows 活动标记禁止重命名/删除及 Unix 标记不跟随链接。

跨进程用例启动实际测试子进程持有上传，验证第二进程清理保留活动数据；强制结束拥有者后回收已识别正文/标记，并保留额外文件；后续上传使用新 UUID 且正常工作。另在父进程持有上传时启动闲置子进程，父进程关闭上传后目录应可删除，证明闲置子进程没有继承并钉住这些句柄。用例仅使用专用临时资料，等待与失败有界，不用模拟锁接口。

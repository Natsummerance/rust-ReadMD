# 第三批增量：UnicodeMath 语义、源码定位与公式导入

本增量属于 R007/R008/R059，第三批完整范围及其他未完成项不变。依赖使用纯 Rust 与现有离线数学资源，没有引入 Office、Python、Node 或外部公式引擎运行依赖。

## 问题与实现

旧 `from_unicode` 将上下标当成独立字符串，`x^2/y` 的分子实际成为 `2`，`x` 落在分式之外。已通过修复前的真实 Rust 回归复现。旧路径还把 UnicodeMath 转为 TeX 再生成 OMML，丢掉原始节点范围，所有 UnicodeMath 节点列表为空。

新的 `unicode_math.rs` 将线性输入解析为带原文位置的结构，再复用 `math_dsl` 的结构编译和 schema 校验。生成的 DSL 只是内部编译输入，节点及槽位范围重新映射到原文 UTF-16，不对原文做字符串查找。旧公开 TeX 投影函数也调用同一编译器，避免两套优先级实现。

当前增量覆盖四类分式、分式左结合、同类上下标右结合、同一基底的混合上下标、前置上下标、括号与隐形分组、平方根与根指数、矩阵/空单元格、方程组对齐、重音/横线/花括号、边框、大型运算符及其上下限。补充原文诊断与字节/节点/深度预算。未识别的命令保留原文并返回精确诊断，序列化拒绝将其当作已支持公式。

普通槽位编辑保持 UnicodeMath 原文；复杂属性操作返回可读 DSL，不暴露 XML。槽位输入复合加法或分式时保留操作数边界，已有语法括号不重复添加。

前端复用现有公式源码区：完整 MathML 或具有明确 Office 结构标识的线性公式可直接粘贴，自动转换为可读 DSL。不会重新解释插入到已有源码中间的片段；普通 LaTeX 粘贴保持兼容。转换失败保留粘贴文本、禁用确认；关闭、输入或开启另一草稿后，旧响应不可写入。旧 LaTeX 公式转换后使用 DSL 包裹，不能把 DSL 写进 `$...$`。

原生检查还发现结束边界误选：光标刚好位于公式之后时，插入命令误打开前一条公式。已区分折叠光标的结束位置与公式内部，显式选择完整公式仍能编辑。导入会清理旧源码输入的待执行防抖，避免旧渲染使新导入失效。

## 验收边界

本增量不能视为完整 UTN28 或全 OMML 兼容。函数字形/应用、所有 n 元操作符标志、尺寸间距、组合文字、其他少用线性构造和全部符号行为仍需继续扩展；MathML 原始 XML 精确源码映射也仍未完成。实际 Word 应用往返、触控/输入法/辅助技术全矩阵、其他平台原生验证保留为未验收。

独立 PDF 检查确认了矢量公式的画面和普通正文的 Unicode 提取；公式轮廓不能完整提取为数学文字，不能以视觉正确冒充可搜索/可复制的公式语义。当前增量使用标准 Base14 西文字体，以及内嵌的中文/数学字体子集，不宣称所有字体均已嵌入。

语义依据：[Unicode Technical Note 28 v3.3](https://www.unicode.org/notes/tn28/UTN28-PlainTextMath-v3.3.pdf)；[Microsoft 线性公式输入说明](https://support.microsoft.com/en-gb/word/linear-format-equations-using-unicodemath-and-latex-in-word)。没有导入第三方 UnicodeMath 解析器。

# V0.0.5 第三批：Windows 沙箱资源恢复与真实 TeX 长路径

日期：2026-10-11。B3-52 限定增量，第三批仍进行中。没有更新已安装软件、发布版本、添加依赖或增加构建目标。全部编译使用现有单一 target、锁文件和离线模式。

## 实际改动

受管理 TeX 的编译和就绪探测现在共用持久任务归属。成功创建的 AppContainer 配置和两个 DOS 路径映射分别登记到同步日志，名称严格绑定该任务 UUID；其他用途和不匹配名称拒绝登记。子进程继承任务租约，沙箱存活期间保留任务归属。下一次真实应用启动先确认拥有者已停止，再回收已确认归属的配置和映射。

回收只删除日志登记的当前用户配置，以及名称和目标都匹配的 DOS 定义。同名但不同目标的映射、其他活动拥有者、未知日志和非空租约文件保留。对应 Windows API 的删除行为见 [DeleteAppContainerProfile](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deleteappcontainerprofile) 与 [DefineDosDeviceW 精确目标删除](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-definedosdevicew)。API 创建成功到归属日志落盘之间仍有未覆盖的崩溃窗口，不能按名称前缀认领遗留资源。

真实大包安装暴露出旧字体代码无法读取长运行库路径的问题。当前增加任务内的短普通文件系统资源引用，由相同归属日志管理；不复制运行库，访问权限只授予该任务。编译程序仍从受管理隔离入口执行。字体、Fontconfig 和 kpathsea 使用短资源路径，任务回收仅移除引用，保留真实运行库。

同时修正两处 Windows 路径差异：CMap 的根和子文件使用相同原生规范路径表示，仍执行原有包含范围检查；目录引用登记先比较解析后的目标，再保存 Windows 实际返回的原生目标拼写。回收不依赖已消失目标的解析结果。

## 此前为什么没有发现

原先低层探测和单元材料使用较短的运行库目录；真实 v2 安装事务生成更长路径，首次实际安装因此在字体查找失败。引入短引用后，实际安装又发现 CMap 长子路径与短根路径的规范表示不一致。完整内核回归随后发现引用目标记录与 Windows 原生读回拼写不同，导致回收保守保留。

这三次失败分别补充了运行库路径、实际原生引用和完整回收测试；修改源码并重建后才取得当前通过结果。早期测试还错误地重新打开活动日志写入器，触发 Windows 共享保护；只修正测试读取方式，没有放宽日志锁。失败日志保留，不将失败后的原样重试计作修复。

## 现有调用链与缺口

`main.rs` 的 `py.rename_file(path,new_stem)` 桥直接调用 `/api/rename`，没有传入打开时的修订或文件身份。`server.rs::h_rename` 限定同目录、同扩展名，校验名称后移动文件，再尽力同步部分近期记录和设置；目前不迁移 `authorized_save_paths`，也不迁移持久审阅路径。

`GET /api/file` 是现有保存授权的来源。`h_save` 在取得 `document_history::SAVE_LOCK` 之前读取授权状态；`h_rename` 和 `review_api::handle` 的 `open/resume` 当前没有参加这一锁协议。因此只给重命名加锁或只更新一次授权集合仍不够：

- 保存可能在等待锁之前已记住旧路径可写，随后在文件移动后继续执行。
- `review open` 可能在重命名查不到旧会话之后、实际移动之前，刚好为旧路径创建持久会话。
- `GET /api/file` 的存在检查、授权登记和读取也可能穿过重命名，重新登记已移动的旧路径；不能把这个入口排除后声称授权生命周期已经闭环。
- 同资料目录的另一内核进程有自己的内存授权集合。本进程删除旧授权并不会撤销另一进程里的旧授权。无修订条件的旧路径保存是否可重建旧文件，必须单独覆盖。

这些并发风险来自源码分析，本轮没有稳定注入并真实复现，不能和上面两个已复现产品失败混计。

进入常用文本的编辑器会调用 `ReadMDReview.mount`，进而 `open` 持久审阅；这不要求用户先启用 AI 或插入待审块。普通保存也不会删除会话。因此，“有持久审阅就先拒绝重命名”只覆盖首次编辑前等较窄流程，不能被描述为已完成日常编辑后的重命名。

前端标签缓存、`ReadMDReview` 的每标签记录和普通历史的 `recoveryKey` 还各有路径身份。完整实现须验证这些对象，而非只修改标题和 `tab.path`。本轮不修改前端或语言文件。

`app.store.rename_document` 只更新其数据库内的记录，不改引用文档正文。`/api/links/index`、反向链接使用的 `LinkIndexer` 还有独立索引数据库；重扫索引也不能修复 Markdown 原文中的旧链接。多文件引用预览、修订检查、写入及回滚继续为单独待办，V6-31 不因此完成。

## 可分步实施的用户流程

第一步只考虑已打开、当前没有未保存修改、尚无持久审阅的单个文本文件：

1. 用户在标签上发起重命名。调用方携带其打开时的修订／预期路径身份；排队期间切换或改变文档不能改到另一文件。旧桥参数的兼容或明确拒绝策略须一起落地，不能暗中把磁盘重读当作用户已确认的新修订。
2. 后端取得统一协调权限后，重新校验源文件存在、源路径授权、目标范围、名称和预期修订；同时检查旧／目标路径及 `pending_path` 上的审阅记录。
3. 任一路径存在持久审阅，或审阅存储不可确定时，在任何文件移动之前拒绝。预定稳定错误为 `rename_review_session_active`；现有成功 HTTP 状态加 `ok:false,code,error` 的返回族可保留。准确提示为“文档已有持久审阅记录，当前不支持重命名；原文件和审阅已保留”。不能提示“保存后重试”，因为保存不会清除此状态。
4. 使用系统原子的 no-replace 移动；成功后才迁移本进程精确授权。失败不得增加目标授权、撤销源授权、改写审阅、生成隐藏中转文件或覆盖目标。
5. 调用方只在明确成功后更新标签与路径身份。继续编辑、保存、关闭、重开和重启必须通过同一目标路径；保存冲突保留磁盘及未保存内容。

有持久审阅的常见编辑流程需要第二步独立实现可靠迁移，不能借第一步的拒绝路径算作完成。第一步的跨入口协调若尚不能证明，保持现状并保留首败，也不能只上线局部授权补丁。

## 锁方案与可用性边界

优先评估每个规范化资料目录一个固定、空的 `document-operations.lock`，不按已打开文档散列创建永久锁文件。锁文件不含 PID、路径清单或正文，不删除，不用“过期 PID 清理”接管。系统句柄在退出或崩溃后释放；固定文件空间为每资料目录一个文件。复用仓库现有系统锁的约定，不直接借用协作数据库的生命周期写入者租约或能力包资源名。

Windows 需检查取得句柄的实际对象为普通、非重解析、空文件，拒绝目录、重定向和已有非空对象；Unix 使用 no-follow／close-on-exec 及系统独占锁，并验证实际对象。目录别名须收敛到同一锁对象。锁失败不能当作保护成功，更不能覆盖失败锁对象。

建议顺序为 `SAVE_LOCK → 资料目录系统锁 → 授权集合或单次审阅存储事务`，释放按相反顺序。所有需要的调用入口须审查同一顺序，包括桌面桥和 MCP 的真实适配路径。不得把系统锁持有到网络请求、AI 调用、弹窗、文档转换或等待前端确认期间。

需要一起纳入或明确安全拒绝的入口至少包括：

- 重命名的鉴权、审阅检查、移动和授权迁移。
- 审阅 `open/resume` 从重新鉴权、读取实际字节至查找／创建完成；草稿没有磁盘重命名问题，可评估独立路径。
- `/api/save` 的授权决定、修订检查和文件提交；不得在锁外缓存旧的授权结果。
- GET/file 的文件存在性与授权登记竞争。锁只覆盖必要的短入口；内容描述、转换及大文件读取应在明确的读取一致性协议中处理，不能把整个转换期间变为全局阻塞。
- Save As、文件副本、转换输出、导出及其他可能创建／覆盖旧或目标路径的入口。当前只有部分入口使用 `SAVE_LOCK`；不能由此推断它们已参加跨进程协议。

跨进程锁竞争须有限等待，例如最多 3 秒后以稳定 `document_operation_busy` 失败；实际时限及各响应族统一后用真实进程验证。锁异常用明确存储错误，不回退到无锁写入。普通开／存的可用性与延迟必须一起验收，不能为重命名引入持续的普遍阻断。

资料目录锁只协调遵守协议且使用同一资料目录的新版内核；同一工作区使用不同资料目录、旧版内核或外部编辑器不参加。它本身不能构成所有程序间的文件事务。若不能形成可解释且可验证的安全边界，应继续拆分或暂缓该实现。

## no-replace、外部修改与恢复

目标存在性预检不能防止其后出现的目标。Unix 的 `std::fs::rename` 可覆盖后来出现的目标，禁止作为 no-replace 的回退。应复用系统约定：Windows `MoveFileExW` 不带 `REPLACE_EXISTING` 及复制删除回退；Linux `renameat2(RENAME_NOREPLACE)`；macOS `renameatx_np(RENAME_EXCL)`。不支持可靠原语时在移动前明确拒绝。

大小写重命名必须避免“旧路径 → 临时路径 → 新路径”的不可恢复间隙及可能覆盖目标的回滚。本轮 [Win32 独立探针](../../.cache/capability-upgrade/rename-native-case-probe-ri98hbf6/report.json) 证实 `MoveFileExW` 不带替换标记可直接把合成 `Case.md` 改为 `case.md` 并保持字节。它仅证明该 Windows 原语的这一例；没有证明 Rust 后端集成、后出现目标的竞争、Unicode／别名情况或任何非 Windows 平台已通过。

源路径外部更改、替换、链接／父目录重定向、大小写敏感目录和硬链接别名必须有明确策略及原生测试。文件修订检查与移动之间仍存在外部竞争，资料锁不能约束外部程序；不能把哈希预检描述为所有进程的原子比较交换。无论策略如何，不覆盖第三方目标、不删除无法识别归属的文件始终是硬边界。`.bak` 是独立可失败伴随项，冲突时保留双方并返回准确警告，不使用覆盖移动。

持久审阅目前的 `prepare_save`／`commit_save` 不是通用重命名事务：预留额度不保证提交不再失败，文件移动后到提交之前可能崩溃或发生 SQLite 持久化失败。现有 `by_path` 同时查 `pending_path`，`review::open` 对符合 SaveIntent 预期字节的目标可恢复提交，这是后续可利用的线索，不能直接等同于已有审阅的安全迁移。

完整迁移须分别保留磁盘基线、未保存审阅内容、待审原文、撤销／重做及幂等回执，且不能把用户未保存内容顺便写盘。需持久化可识别的迁移意图；在移动前失败保持原文件与旧审阅；移动后、数据库提交前失败必须能在重启时根据实际文件身份／字节恢复或进入保全冲突状态。旧、新路径同时出现外部文件时不得自动覆盖或清除任何一方。没有验证这些恢复点前，仍采用移动前拒绝持久审阅的窄边界。

## 真实进程与原生复测方法

每次生成新的合成资料目录及 `old.md`／冲突文件；预先记录字节散列，不复用或清理首败资料。使用已构建候选：`readmd.exe --no-window --port -1 --data-dir <独立资料目录> --workspace <合成文档目录> --assets <仓库 assets> --require-token --print-token`。令牌只保存在探针内存，报告只保存脱敏状态、稳定错误码及字节比对，禁止记录 stdout 全文或请求头。

首败一按“GET old → rename → 直接 save new → review open new”重跑；首败二按“GET old → review open old → rename → GET new → 读取同一 document_id → 携带该审阅 CAS 的 save new”重跑。第一阶段预期首败二变为移动前的明确拒绝，不能仍移动文件后靠保存失败保护。另保留原报告，不用新候选结果回写旧报告。

之后用两个真实候选进程及同一合成资料目录完成系统锁、旧授权、review open 和保存并发；按规范边界屏障重放矩阵。退出核对仅限本轮拥有的进程和目录，不杀用户进程，不递归清理未知资产。完整 UI 流程还需通过现有原生桌面测试通道验证标签双击／F2、编辑态、脏文档、保存、重启恢复和本地化提示；HTTP 结果不计为这部分通过。

本轮唯一结论是两类生命周期问题真实存在，局部授权迁移不足以安全修复。工作区多文件引用更新、持久审阅可靠迁移、GET/file 授权竞争及跨平台恢复均继续待办。

## 后续设计评审：支持常见已保存审阅的最小闭环

以下是 2026-10-27 后续只读设计评审，**尚未实施或验收**。它替代上文初版“所有持久审阅一律拒绝”的拟交付范围；上文首败和待验项保持有效。没有因本评审修改公共 Rust 源码或运行 Cargo。

建议第一步真正交付“普通文档正文已保存 → 退出编辑 → 重命名 → 继续编辑保存 → 关闭／重启恢复”，同时支持尚无审阅和已有已保存审阅两种情况。初始格式限定为现有可保存的 Markdown／文本扩展名，源必须是允许的文档根内普通文件，排除资料目录、任务输出和已知托管资源，保持同目录、同扩展名。常见审阅会话必须保留同一个 `document_id`、待审原文、changes、undo／redo、mappings 和 checkpoint，不能删会话再开新会话。

“已保存”由服务器在统一协调范围中检查：磁盘原始字节散列等于会话 `disk_revision`，解码规范化正文等于 `session.content`，且无其他 SaveIntent 或 recovery。不能只依赖 `tab.isDirty`。决策元数据已持久化且正文相同可以保留；元数据迁移不能顺便把 checkpoint 改为当前决策。前端在捕获身份前等待现有队列完成，后端仍用 generation／review_revision CAS 防止并发变更。

未保存正文、外部改变、在途保存／恢复和不支持的文件身份均在移动前明确拒绝。对于“未保存”可以准确提示保存后退出编辑再试；对于在途恢复则须提示先处理恢复，不能伪装成普通脏文档。有持久审阅本身不再作为第一步的统一拒绝理由。

第二步才扩展未保存审阅正文的重命名、文件重命名撤销，以及多文件链接内容更新。第一步不能算完整 V6-31；但只要其全部协议及入口通过验收，就能解决目前两个真实首败的常见已保存流程。

### 可复用与不可直接复用的 SaveIntent 行为

| 现有行为 | 第一阶段用法或限制 |
| --- | --- |
| `prepare_save` 的 CAS、pending_path 预约、阻止并发 review mutation、预算与幂等回执 | 复用框架；在一个 SQLite 事务内建立明确的 rename 意图，不能先写另一份独立 JSON 日志再期待两者原子一致 |
| `SaveGuard::prepare` | 不直接复用。它会执行资源／数学转换计划及编码，重命名必须保持原始磁盘字节，不能变成一次隐式保存 |
| `finish_intent` | 不能原样用于 rename：它更新 checkpoint，可能改变后续 discard 的边界。需 metadata-only 分支，只迁移路径并写 rename 事件，保留原 checkpoint 及整条审阅状态 |
| 目标 hash 和正文相同时 `open` 自动完成 SaveIntent | 不足以证明文件移动。第三方可以在目标创建相同字节的另一文件；恢复必须验证源、目标两端及持久文件身份 |
| 打开源时发现不同 target 的 intent | 现有分支标记 `save_target_unchecked`；移动前崩溃不能只依赖它恢复，需要 rename 专属的两端检查／安全取消 |
| 预留完成额度 | 仅是预算预检。提交仍可能 I/O／SQLite 失败；必须保留意图及后续恢复，不能把预算预检当作原子性证明 |

优先在现有 SaveIntent 增加明确操作类别及源身份／目标初态，或在同一个 review SQLite 事务中建立带 `intent_id` 的 rename 记录。普通 save 默认维持原语义。操作类别不能被旧内核忽略后按普通保存恢复；应评估提升 review schema 版本，让不识别 rename 意图的旧内核拒绝打开，而非猜测恢复。升级需先停止旧内核。

没有审阅记录的显式重命名可以在同一事务中建立干净会话和 rename 意图，使成功与崩溃路径共用同一协议；这只发生于显式修改，不使普通阅读／resume 创建持久审阅。预算不足须在移动前失败。持久意图最多一个／文档，未解决 rename 的资料级数量设明确上限；不得通过新增无上限路径文件来存储状态。

### 恢复状态与用户反馈

操作使用由调用方生成的稳定 `operation_id`；重试绑定原源身份、修订及目标，相同 ID 配不同请求明确拒绝。客户端在发请求前保存待确认的 ID，避免文件已移动而成功响应丢失后仍只恢复旧路径。状态查询返回操作结果，不能让 operation_id 本身授予磁盘访问；目标仍通过正常、鉴权的文件打开流程取得授权。

| 持久状态与两端事实 | 恢复策略 |
| --- | --- |
| 未建立意图，或准备提交失败 | 未移动；源、目标和审阅不变 |
| 已建立意图，源仍为原身份／原字节，目标缺失 | 安全取消 rename 意图，保留源及全部审阅；取消的数据库提交失败时继续保留意图并明确等待恢复 |
| 源仍为原身份，目标为第三方对象，包括相同 hash | 移动没有被证实；不迁移审阅或授权，不删除目标；可安全取消或报告冲突 |
| 源已消失，目标身份正是原源对象且字节吻合 | 完成 metadata-only 审阅迁移；重复恢复幂等，不更改正文、checkpoint 或撤销链 |
| 源与目标均存在、均消失、身份不吻合、文件被外部修改 | 保全冲突，不猜测、不覆盖回滚、不删除任何一端；提示用户处理恢复 |
| 审阅提交已完成，响应或本进程授权更新未完成 | 根据持久操作结果重新打开真实目标，再更新标签；不再次执行文件移动 |

大小写重命名不能用“旧路径不存在”判断结果，需验证实际目录项大小写和对象身份；第一阶段若尚无平台原生证据，则在移动前明确拒绝这一类，不能转回两步临时名称。

文件已移动但审阅提交失败时不能简单返回普通“重命名失败”并让标签继续编辑不存在的旧路径。返回明确的 `rename_recovery_pending`、`moved:true`、操作 ID 和经过验证的当前目标；客户端保留原内容并显示“文件已移动，审阅信息待恢复”，暂停写入相关两端，提供重试／重新打开。不能输出“已全部完成”，也不能使用可能覆盖后来出现的源文件的自动回滚。普通读取和其他不相关文档继续可用。

### GET/file 的短协调方案

不持有资料锁执行 `content::describe`、转换或大文件处理。先捕获文件身份，在锁外生成内容，再在短 gate 内重新核对实际路径身份／修订，最后登记保存授权并返回匹配的身份。若读盘期间文件移动或被替换，返回准确的失效结果，不在最后登记旧路径。重命名的授权迁移使用同一个 gate；因此“GET 完成前线性化”或“rename 完成后 GET 重新验证失败”均可解释。

授权集合需绑定实际已打开的文件状态，不能仅把路径字符串永久视为可创建文件的能力。旧授权保存要在取得 gate 后重新校验；正常保存成功后更新其身份／修订。预期已有文档的保存和显式 AI 派生／另存创建须区分，避免旧路径失效后自动创建，也避免把正常创建误拒绝。被其他进程更改的授权不能只依靠本进程删除集合来撤销。

### 跨进程入口及精确所有权建议

仅靠 `server.rs::h_rename` 和 `review_api.rs::open` 不能完成这一闭环。以下是本次源码追踪定位的入口；实施时须将所有能落到支持路径的调用闭合到一个提交边界，并用源码库存检查防止遗漏。现阶段没有占有或修改这些共享文件。

| 文件所有权 | 必须协调的窄入口 | 不能依赖的假设 |
| --- | --- | --- |
| 新 `document_operations.rs`；`lib.rs` 只注册模块 | 固定资料目录锁、文件身份、no-replace、明确的 existing／new 提交能力 | 不能在通用 `content::write_bytes_atomic` 无条件套锁：它没有资料身份，也写配置／历史，可能引入反向锁顺序 |
| `server.rs` | h_rename、h_file 最终授权、h_save 锁内重新鉴权、save_document_copy、save_document_assets_locked、h_file_save_fixed；h_export 最终发布、h_image_save，以及可与支持路径相交的上传提交 | 弹窗结束／渲染结束以后仍须复验目标；只提前拿一次“可覆盖”布尔值不够；保留现有转换暂存改动 |
| `review.rs` | rename 类意图的准备／提交／取消、metadata-only 状态迁移、专属恢复和幂等状态查询 | 普通 finish_intent 会改 checkpoint；不能直接调用后称完全保留审阅语义 |
| `review_store.rs` | 同事务意图存储、路径预约／查询、字节和数量上限、schema 兼容拒绝 | 不能另开独立日志数据库后假设跨数据库提交原子；pending 状态不作为普通历史清理 |
| `review_api.rs` | open／resume 进入前的短协调、丢失旧路径时先检查 rename 恢复、返回结构化状态 | 不先因磁盘缺失退出，再期待服务层见到恢复请求；不在审阅事务内部倒序获取 SAVE_LOCK |
| `convert.rs`；`batch2.rs` | write_md_managed／locked 和 save_converted_assets；同步转换与后台批量转换的实际写入阶段 | 后台线程不能由 HTTP 请求入口的锁替代；不持锁做 OCR、解析或模型工作 |
| `document_intelligence.rs` | edit_document 真正提交路径 | MCP／Extension Host 的此工具直接调用该服务，没有经过 h_save；已有 SAVE_LOCK 只是进程内锁 |
| `export_snapshot_api.rs`；必要的 `mcp.rs`／`mdexport.rs` 发布适配 | 导出最终目标的 expected-before 复验及提交 | MCP 的 write_output 部分绕过 h_save；格式／扩展名确实排除的目标可不参加，但必须由验证证明，不按通常 UI 用法假定 |
| `main.rs` 桥；`assets/js/core/tabs.js`、`reader/render.js`、`editor/review.js` 及会话／恢复保存入口 | operation_id、预期修订和 review CAS；脏／在途状态；成功或待恢复后的同一标签及审阅身份；重启待确认操作恢复 | 不只修改标题；双击／F2／非活动标签入口同样保护；不丢弃旧回执、队列或恢复正文 |
| 新专属 Rust／HTTP／原生测试及本地化所有者 | 下列屏障测试和稳定提示 | 接口模拟不计原生重启成功，Windows 成绩不计 Unix |

托管资料目录、更新下载、配置／历史写入、私有任务输出、PDF 等非支持格式，应通过明确路径／格式准入排除重命名对象，避免为了这一切片给所有内部写入套锁。邮件附件等派生写入若目标可能与准入路径相交，也须加入实际提交适配，不能按文件名随机就当作不可能。现有代码执行工具启动的外部程序不遵守资料锁，按外部修改处理，不宣称全系统事务。

同一新版资料目录的多个内核／MCP 进程遵守固定 gate；不同资料目录访问同一工作区、旧版内核、外部编辑器和代码子进程不受它约束。对这些情况只承诺 no-replace 不覆盖目标及明确的外部改变冲突，不承诺跨资料目录分布式事务。已移动但字节异常时保留目标和意图，不能把它冒充已保存审阅。若产品要求同时协调不同资料目录，需要另设工作区级身份和锁协议，不能假装每资料目录锁已解决。

锁仍为每资料目录一个稳定空文件，不含路径或路径散列名，不随文档数量增长；仅在短提交段持有。持久意图里的完整路径仅保存在现有本地私有审阅存储，不写临时公共文件、报告、日志或发布材料。完成回执及历史服从既有有界存储；无法安全清理的待恢复意图保留并按上限拒绝新 rename，不能删掉恢复信息换取继续成功。

### 确定性风险审查与实施门槛

| 精确交错／故障点 | 仅局部修补的结果 | 必须对应的测试或保护 |
| --- | --- | --- |
| GET is_file 后停顿 → rename 移动及撤销旧授权 → GET 登记旧路径 | 旧授权复活 | h_file 最终验证和登记同 gate；双线程屏障＋双进程复验 |
| save 锁外读取 authorized=true → rename → save 发布 | 旧路径可能被重新创建 | 授权及存在／修订决定移入 gate；覆盖无 expected_mtime 的旧协议及合法派生创建 |
| review 读盘后停顿 → rename lookup 无记录 → review open 持久化 | 产生悬空旧会话 | open 的查找／创建与 rename 预约同一协调协议；测试不靠 sleep 命中 |
| rename 意图提交后强杀，尚未移动 | 当前通用 open 只标 save_target_unchecked，不能自动解除 | 源身份不变＋目标缺失时专属取消，保留完整审阅；取消提交失败再重启 |
| 目标出现相同字节的第三方文件 → no-replace 失败 → 取消前强杀 | 通用按 hash 恢复可能错误迁移到第三方 | 同 hash 不同文件 ID 的真实目标，源／目标同时核对，绝不只凭字节提交 |
| 文件移动后强杀，或 commit SQLite 故障 | 文件和会话位于不同路径 | 原生进程终止＋合成 SQLite 提交故障；重启完成 metadata-only 迁移，待恢复期间不覆盖回滚 |
| 普通 saved review 存在 undo／redo、checkpoint 后的纯元数据决策 | 复用 finish_intent 可能改变 discard 边界 | rename 前后完整快照／历史比较；同一操作的 undo／redo／discard 在重启后仍正确 |
| 响应丢失／客户端持久会话尚未改新路径 | 重启只打开旧路径而丢掉当前标签 | 发请求前保存 operation_id，恢复查询定位目标，再正常 GET 授权；相同 ID 重试不移动第二次 |
| 弹窗确认或长转换后才提交，期间 rename 完成 | 旧的目标判断被缓存，可能覆盖或重建路径 | 各实际提交入口的 expected-before 复验；长工作在锁外，短提交内重新决定 |
| 正常并行开／存，无 rename；故意占锁及强杀释放 | 新 gate 可能造成普遍堵塞或遗留阻断 | 普通可用性／延迟、明确有界 busy、固定锁文件数、进程退出后接手，均用真实进程测试 |

此矩阵是基于源码的确定性失败推演，尚不是这些并发失败的实测报告。下一轮先落地并验证协议／恢复单元，再接客户端闭环；在所有必需入口、schema 兼容及原生恢复通过前，不开放“已安全修复”的成功路径，也不把已有打开／保存功能转换为长期持锁流程。

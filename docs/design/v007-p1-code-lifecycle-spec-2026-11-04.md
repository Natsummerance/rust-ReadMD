# V0.0.7 P1 代码运行生命周期

本切片承接 V7-05，复用现有 `/api/code/run`、任务取消、文档修订和补偿历史，不重新建设代码工作台。未通过下述完整链路前，不标记 V7-05 或全部 P1 完成，不发布 V0.0.7。

## 输入、行为与独立预期

1. 运行前已取消：有效 SQL 和真实子进程命令均返回 `execution_cancelled`，不创建脚本或启动运行资源，不返回成功输出。
2. 运行中取消：固定的长递归聚合 SQL，以及仅等待后输出 `LATE` 的专用子进程。取消信号应在 200ms 内被观察，返回前完成该请求执行资源的回收；worker 停止目标为 2 秒。不得清理其他进程、用户模型或其他请求。
3. 超时：使用相同固定输入和独立期限。返回 `execution_timeout`，SQLite 不再留下后台查询；子进程及它持有管道的子孙不能继续运行。取消、超时、执行错误和成功保持不同状态。
4. HTTP/MCP：正式鉴权、已有确认闸门和请求预算保留；可取消请求使用现有 task ID，MCP 的外部取消传到同一执行实现。取消后不插入正文。重复 ID 不能让旧 worker 成为不可取消的执行者。
5. 固定目标：开始运行时绑定文档身份、内容修订、generation、代码围栏的 UTF-16 范围及预期原文。切页、编辑、移动围栏或切换编辑器后，旧结果不能写到当前文档或按重复字符串误匹配。
6. 成功结果：结果写入由 Rust 文档事务处理，显式插入构成一次撤销；保存、关闭、新进程重开、撤销及重做都保留正确内容与待审状态。运行成功不等于结果已插入或保存成功。
7. 环境：内置 SQLite 可实际就绪。其他语言检查真实最小操作，宿主 PATH 能找到程序不能作为受管就绪证据；未有锁定运行资源时明确限制，不宣称自包含。不得静默下载、加载模型或替用户安装解释器。

## 实施顺序与证据边界

先固定取消/超时首次失败，再修复执行生命周期，随后接入目标修订与结果事务。保留现有正常 SQL 渲染和语言兼容回归。Mac 本地共享 target 离线构建；Windows/Linux 使用各自原生 CI 的进程和 SQLite，不能用交叉编译结果代替。

SQL 优先复用锁定 rusqlite 对 SQLite 的 progress handler，直接在当前请求中运行和中断，避免超时返回后遗留脱离生命周期的线程。参考：[SQLite 查询进度回调](https://sqlite.org/c3ref/progress_handler.html)、[SQLite 中断语义](https://sqlite.org/c3ref/interrupt.html)。子进程以请求持有的专用进程组或系统对象管理，不能向宿主进程组发送信号。

内存 SQL 的 ATTACH/VACUUM INTO、目录 PRAGMA 与动态扩展不能成为读写外部文件的旁路；显式内存数据库仍可使用。MCP 的取消通知按已有协议不再回复原请求，使用后续请求和正常 EOF 等待 worker 的真实停止，不能把“没有响应”误判为运行故障。Mac 进程组只剩已退出成员时的 EPERM 必须由原生组成员状态确认，不得一概忽略。Unix 保留可等待的根进程至发出组信号，避免先回收 PID 后误伤复用同号的进程。

真实原生 UI、完整语言矩阵、受管运行资源和跨进程结果历史均须另取证；本规格不代表它们已经完成。
